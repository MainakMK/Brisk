Brisk — Changing the CDN Base Domain

Runbook for migrating a2zjav.com → a new base domain, while keeping Bunny Smart-DNS for geo-routing. CONFIG + DNS + CERT — no core code rewrite

The one-paragraph answer

The base domain is parameterized, not hardcoded — it lives in a handful of env values, a few Bunny DNS records, a wildcard TLS cert, and each zone's stored hostname. Bunny's geo-DNS "brain" (Smart Records) is reused exactly as-is: the new domain's zone simply lives in Bunny, and the same reconciler writes the same kind of weighted/geo records — only the names change. You migrate by dual-running both domains (old stays live), then retire the old once the new is proven on ≥2 edges. Zero downtime.

Why no downtime: the old domain keeps serving from start to retire. The new domain only needs to be added, never swapped in destructively. A client is only ever sent to a name that already has a working cert + edge vhost.

Detailed steps

  1. Delegate the new domain's DNS zone to Bunny Bunny · you

    In the Bunny dashboard add newcdn.com as a DNS Zone, then point the domain's nameservers (at your registrar) to the Bunny nameservers it gives you. This one move is what lets Bunny do both geo-DNS routing and answer the ACME DNS-01 TXT challenge for the cert. Nothing about the routing logic changes — it's the same Smart-Record engine, just a new zone. Wait for the zone to go live (dig NS newcdn.com shows Bunny).

  2. Issue the new managed wildcard TLS cert + fan to edges control plane .env

    Append the new wildcard(s) to BRISK_TLS_DOMAINS — keep the old ones during migration so both serve:

    # brisk-control/.env  (control plane)
BRISK_TLS_DOMAINS=*.cdn.newcdn.com,*.newcdn.com,*.cdn.a2zjav.com,*.a2zjav.com
BRISK_TLS_STAGING=true   # dry-run on LE staging first; flip to false at cutover

    Restart the control plane → it issues the managed wildcard via Bunny DNS-01 and ships it to all 3 edges over the agent-config channel. The agent already selects the longest-suffix covering cert per zone, so once issued, both a2zjav.com and newcdn.com hostnames are served. Verify in DNS / TLS status and with openssl s_client -connect <edge>:443 -servername x.cdn.newcdn.com.

  3. Point the DNS reconciler at the new zone control plane .env

    Tell the reconciler which Bunny zone + record to manage:

    # brisk-control/.env
BUNNY_DNS_ZONE=newcdn.com          # (or BUNNY_DNS_ZONE_ID for the numeric id)
BRISK_CDN_RECORD=cdn                # label under the zone Brisk routes

    Restart the control plane. The DNS syncer creates the geo/weighted Smart A-set for *.cdn.newcdn.com → your NY / FRA / BLR edges — exactly the same record shape as the old zone (same weights, same health-monitor backstop if enabled). Confirm in the dashboard DNS page and with dig x.cdn.newcdn.com from a couple of regions.

    Heads-up — one zone at a time: the reconciler manages the zone it's pointed at. If you want it to keep maintaining the old records during the overlap, leave the old records in Bunny as static (they don't need active reconciliation to keep resolving) and let the syncer own only the new zone.

  4. Update the dashboard's suggested base domain dashboard .env

    # brisk-dashboard/.env
VITE_CDN_BASE_DOMAIN=cdn.newcdn.com

    Rebuild/restart the dashboard. This is purely cosmetic — it changes what a new zone suggests as its hostname (e.g. my-site.cdn.newcdn.com). Existing zones are unaffected by this value.

  5. Give each live zone the new hostname (dual-host) data

    Each existing zone serves x.cdn.a2zjav.com (its stored cdn_hostname). The safe path is to add the new name beside the old rather than rename in place — add x.cdn.newcdn.com via the zone's Domains tab (it renders as its own SNI vhost on every serving edge, using the new cert). Now both names answer for the same zone. Do not bulk-rewrite cdn_hostname out from under a tenant who has already CNAME'd to the old name — that would break them until they re-point.

  6. Tenants re-point their CNAME tenants

    Anyone who CNAME'd their site to x.cdn.a2zjav.com updates the CNAME to x.cdn.newcdn.com. This can happen gradually — both resolve during the overlap. Tenants on their own custom domains (e.g. cdn.theirsite.com added in the Domains tab) are unaffected: their ACME HTTP-01 certs are independent of the platform's base domain.

  7. Verify, then retire the old gated

    Only once the new domain is proven (see checklist below) do you retire the old: remove *.cdn.a2zjav.com / *.a2zjav.com from BRISK_TLS_DOMAINS and re-issue (drops the old SANs), delete the old Bunny records, and remove the old hostnames from zones.

    Golden rule: never remove an old hostname until the new one is verified serving on ≥2 edges, and never leave any live hostname with zero in-rotation PoPs. Confirm the currently-serving hostnames from the control plane before any removal — derive them live, don't assume.

Don't-forget gotchas

  • Management plane is separate. If the control-plane / agent-tunnel hostname or the ACME-challenge proxy lives under a2zjav.com, that's its own cert + DNS record to migrate — independent of the CDN data plane, and not required for the customer-facing cutover.
  • Apex SAN. Only keep the bare newcdn.com in the cert if you actually serve the apex; otherwise just the *.cdn.newcdn.com wildcard is enough.
  • Zone-create coverage is automatic. The "is this hostname covered by a managed cert?" gate reads from the issued certs, so once step 2's wildcard exists, new zones under the new domain pass with no code change.
  • Staging first. Leave BRISK_TLS_STAGING=true for a dry run (untrusted cert, but proves the DNS-01 + fan-out works), then flip to false and re-issue for the real, trusted cert at cutover.
  • TTL. BRISK_DNS_TTL is short by design (~15s) so the new records propagate fast — but registrar NS-delegation propagation (step 1) can take hours; do step 1 well ahead.
  • Bunny API key is shared. The same BUNNY_API_KEY drives geo-DNS and DNS-01 — make sure the new zone is in the same Bunny account.

Rollback (if the new domain misbehaves)

Because it's a dual-run, rollback is trivial: the old domain never stopped serving. To abort, simply stop migrating tenants and (optionally) remove the new *.cdn.newcdn.com records/SANs again. Nothing about the old a2zjav.com path was changed until step 7, so there is nothing to restore. The edge-level safety nets (agent nginx -t before reload, last-known-good config, never-drop-live-hostname) all still apply.
