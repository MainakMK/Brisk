Brisk · Operations runbook

How a brisk-agent change reaches every PoP

One static binary, built once, rolled one edge at a time behind a byte-identical safety gate — nginx never stops serving.

Last updated 2026-06-15.

The pipeline, step by step

  1. Code changeEdit the Go source under brisk-agent/. Nothing is touched on a live box yet.
  2. Build ONE static binaryCompile once in a golang:1.26 container with CGO_ENABLED=0 → a single brisk-agent-linux-amd64. The same binary goes to every PoP — there is no per-edge build.
  3. Pre-flightConfirm the whole fleet is healthy (3/3 online, none drained) before starting. Never begin a roll into a degraded fleet.
  4. Gated rollout, one edge at a timeWalk the edges in a fixed order (NY → DE → BLR). Each edge passes through the gated sequence below; the next edge is only touched after the current one passes.
  5. Fleet verifyAll PoPs on the new binary, all serving. For data-plane features, also confirm the effect is live (e.g. the new field actually appears in the control-plane DB), not just that the deploy "succeeded".

What happens on a single edge

Each edge is handled by a small deploy script (brisk-control/tunnels/deploy-<feature>.sh <PoP>) over SSH-key auth. The sequence is deliberately boring and idempotent:

1 · Snapshot BEFORERecord sha256(/etc/nginx/nginx.conf) and the current agent sha. This is the baseline the gate compares against.
2 · Stage + back upscp the new binary; copy the old binary to brisk-agent.prev-<feature> and the live config to nginx.conf.bak-<feature>.
3 · Swap (nginx stays up)systemctl stop → mv → start. Only the agent restarts (~6s); nginx never stops and keeps serving the last-good config. On start the agent re-renders, runs nginx -t, and only reloads on success.
4 · Snapshot AFTER + checksRe-read the config sha; assert nginx -t passes, services are active, and /healthz returns 200.
5 · The byte-identical gate

Most agent changes are gated off by default or don't change what nginx renders at all, so the rendered config must be unchanged. The script asserts BEFORE == AFTER:

✓ identical → the change is provably inert on this edge → continue to the next PoP.
✗ drift → something rendered differently → halt immediately and roll back from .prev / .bak, before the next edge is ever touched.

Why this can't take the CDN down

Only one PoP in flightThe other two stay in rotation. A live hostname is never left with zero serving edges.
nginx never stopsThe data plane is independent of the agent — nginx serves throughout the ~6s swap and only reloads after nginx -t passes.
Provable inertnessThe sha gate turns "should be safe" into "is byte-for-byte unchanged", and stops the roll the instant that's false.
Instant rollbackEvery edge keeps the previous binary and config, so recovery is one command — no rebuild, no redeploy.

Worked example — the Tech & runtime card

This card added five fields (nginx / agent versions, OS, kernel, Go) to the agent's heartbeat. Because it touches zero nginx rendering, the gate had to hold on every edge — and it did:

PoPnginx.conf sha (before==after)nginx -thealthz
NY8aa1ac3e…✓200
DE93589c0e…✓200
BLR1ed85e2d…✓200
Why the gate alone isn't enough. The first build (958a3d1b) passed the gate on all three edges — yet the feature was still broken, because the new fields were added to the heartbeat struct but never populated in the json.Marshal literal, so the agent sent them empty. The deploy "succeeded" while the data never moved. The tell was go_version (which is runtime.Version() and can never be empty) showing blank in the DB. Fix → rebuild (958a3d1b → 6e58d0ac) → re-roll (again byte-identical) → all five fields live fleet-wide. Lesson: always verify the effect, not just the exit code.

Self-service production rollout — the design we're building next

Status: design, not yet built. Everything above is today's reality — a push from a laptop over SSH, fine for bootstrap but not for day-2 production. The design below replaces it with a pull-based, self-service rollout: CI signs a binary → it waits in the control plane → you press Deploy in the dashboard (or CLI/CI) → edges pull and update themselves, region by region, health-gated. Nobody pushes to an edge; no edge SSH keys. The only new backend piece is a release store.
